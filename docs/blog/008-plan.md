# Feature 008: Make the architecture auditable and the contract browsable

Feature 008 is a plan for strengthening the boundaries inside Vigo Bus Navigator and making its municipal transit contract easier to inspect. The narrow G2 specification clarification has now been re-reviewed and approved by the Stakeholder, QA Tester, UX Designer, and Frontend Developer. G3 is also approved by its required reviewers: the Software Architect, Backend Developer, UX Designer, and Frontend Developer. Those approvals close the specification and planning gates; they do not mean the planned changes have been implemented. The next phase is task definition, followed by its G4 review.

## Architecture that can be checked, not just described

The scope is every maintained production runtime module under `frontend/src`, including UI, localization, configuration-related runtime behavior, and the service worker. Tests, fixtures, build tooling, generated documentation, and non-executable assets are not runtime modules. The plan estimates roughly 75 source modules and calls for each one to have a single primary responsibility in an exhaustive inventory.

The intended dependency direction is inward. Domain rules stay independent of the browser and external effects; application use cases depend on domain rules and explicit ports; adapters connect those contracts to the browser, municipal source, persistence, or other infrastructure. A narrowly defined composition root wires concrete pieces together—it is not a general exemption for business logic. Each domain rule and application use case is also expected to have an isolated Node test that needs no browser, network, or browser persistence.

The repository already has a Vitest architecture check, but its current coverage is selective and its import patterns are limited. The plan extends that check with TypeScript AST parsing and module resolution, and compares a discovered source inventory against a maintained classification manifest. This is meant to catch cases that a regex or entry-point-only scan can miss: aliases, re-exports, literal dynamic imports, type-only imports, and maintained modules that are not reachable from an app entry point. AST checks for browser and other ambient I/O use in the core complement the dependency graph; the plan also calls for human review of semantic responsibilities because a graph alone cannot tell whether a UI module has taken on a use case.

There is a trade-off here: a dedicated dependency-graph or lint package could offer a ready-made graph, but the research favors existing TypeScript and Vitest capabilities to avoid adding a framework or dependency. That means the project must own clear module classifications and actionable diagnostics. The manifest is not meant to hide difficult cases: unknown or stale entries, unresolved dependencies, and prohibited directions should fail validation.

## A page generated from the contract

The documentation page is planned to be generated at `frontend/public/docs/openapi/index.html` before Vite starts, then copied by Vite to `dist/docs/openapi/index.html` and included in Workbox's precache. The generated public file is git-ignored. This order matters: Vite and Workbox must see the finished page as a public asset, and output cleanup must not erase the intermediate before it is copied. In particular, do not point Vite's `emptyOutDir` cleanup at this generated public intermediate. The generator prepares the page before Vite/Workbox rather than writing into a directory that Vite clears as part of its build. The served route remains `/docs/openapi/` beneath the configured application base path. Its source of truth is the existing contract, `specs/004-vigo-jsp-transit-api/contracts/municipal-transit-v5.openapi.yaml`. The page is a readable representation of that contract—not a new transit API, a proxy, or a backend.

The generator is planned to use the repository's existing YAML parser and contract-validation facilities. It must render operations, descriptions, parameters, request and response schemas, component schemas, references, and extensions, with stable pointers that tests can compare to the source contract. Contract-derived content must be escaped. Before validation begins, generation must clear both `frontend/public/docs/openapi/index.html` and `dist/docs/openapi/index.html`. For every failure class—such as missing or unreadable source, invalid YAML/OpenAPI structure, unresolved local references, or rendering errors—the generator must exit nonzero and report the canonical contract path, the failure category, and corrective guidance. Tests must seed stale files at both locations and verify that both are absent after each failure. The failed build must not be able to proceed to deploy artifact upload. Only after validation and rendering succeed may the generator write a fresh intermediate, preventing a success-shaped stale page from surviving a failed run.

The research considered browser-side YAML fetching and documentation bundles such as Swagger UI or Redoc. Both can add runtime behavior or payload; fetching also creates a browser-time failure mode. A separately maintained HTML file could drift from the canonical contract. Build-time generation avoids a docs runtime bundle or remote resources and keeps the contract canonical. It does require tests for completeness, determinism, and failure behavior.

Static hosting adds a routing constraint. The deployment already uses `VITE_BASE_PATH=/vigo-bus-navigator/`, while root hosting must remain supported. The plan makes Vite's base derive from that setting, defaulting to `/`, and keeps app assets, PWA configuration, and documentation route checks aligned. A real directory-index file is important: direct navigation to the nested docs URL must return the documentation, not depend on the SPA shell fallback. The `/docs/openapi/` route must also be excluded from Workbox's SPA navigation fallback so that the app shell cannot replace the document. Checks are planned at root and non-root paths both without a service worker and while controlled by the active worker; they must confirm that direct requests return the contract page, not the SPA shell.

## README and acceptance are part of the design

The README is to be reorganized around purpose, architecture, OpenAPI documentation, setup and validation, data and privacy constraints, and project status and licensing. This is not a license to shorten away important caveats: the existing hosting, security, privacy, source, and transit-data limitations must remain accurate. Its description of harness actors and gates must match and link to the authoritative [Harness Charter](../harness-charter.md), rather than create a competing summary. For README accessibility, native focus styling is determined by the Markdown renderer; the design calls for verifying that visible native focus behavior instead of implying custom CSS can be applied to repository Markdown. Findability will be measured with five people unfamiliar with the repository and uninvolved in the feature. Each gets only the README and 60 seconds to find five specified items; at least four must find all five.

Accessibility is a requirement for the eventual page, not a result this planning document can claim. The design maps verification to applicable WCAG 2.2 AA criteria, including semantic structure and reading order (1.3.1, 1.3.2), contrast and text reflow/enlargement (1.4.3, 1.4.4, 1.4.10, 1.4.11, 1.4.12), keyboard access and focus order, visibility, and unobscured focus (2.1.1, 2.1.2, 2.4.3, 2.4.7, 2.4.11), link purpose and names (2.4.4, 2.4.6, 2.5.3), target size (2.5.8), and names/state for any implemented controls (4.1.2). Page controls must have 44 CSS-pixel touch targets under the project constitution. The planned page uses no motion; if motion is added later, it must honor `prefers-reduced-motion`. Existing Playwright and Axe facilities are planned for automated checks, with manual keyboard, screen-reader, focus-not-obscured, contrast, and responsive review at G5. README checks account for the renderer's native focus behavior. Automated scans alone will not establish WCAG 2.2 AA conformance.

The generated page is static HTML with no runtime contract renderer, so it has no reader-facing runtime rendering error UI. Contract and rendering failures are build-time failures with diagnostics for maintainers. G5 will verify those build failures separately; it will not test a nonexistent unavailable-page UI. The quickstart describes validation to run after implementation: typechecking and tests, contract validation, deterministic generation and failure-case checks, production builds at root and non-root paths, direct-route checks with and without a controlled service worker, and browser/accessibility validation. These are planned checks, not test results reported here. The data model also makes clear that this feature adds no persisted application entities or user data.

## A brief glossary

- **SDD**: Spec-Driven Development; work proceeds through explicit specification, planning, and later delivery gates.
- **Harness gate**: A review checkpoint where assigned project actors record a verdict; a gate is not closed just because a plan exists.
- **Port**: An application-facing contract for an external capability, allowing core behavior to be tested without its real infrastructure.
- **Adapter**: An implementation or entry point that connects an external system or user interface to those inward-facing contracts.
- **Composition root**: The narrow place where concrete adapters and application behavior are wired together.
- **Canonical contract**: The authoritative OpenAPI YAML from which the documentation page is to be generated.
